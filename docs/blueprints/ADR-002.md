# ADR-002 — Core Domain

## Status

Aprovado.

## Objetivo

Definir o Core Domain do Projeto Turistei e estabelecer as regras centrais que orientarão banco de dados, RLS, Edge Functions, frontend e módulos futuros.

## Decisão

O Local é o Aggregate Root principal do ecossistema Turistei.

Todo negócio, ponto turístico, experiência, serviço, comércio, hospedagem, gastronomia, evento ou atrativo será modelado a partir de Local.

Não será criada entidade principal paralela para representar o mesmo negócio.

## Entidades principais

- Local
- Usuario
- Perfil Empresa
- Plano
- Contrato
- Categoria
- Servico
- Agenda
- Disponibilidade
- Reserva
- Pedido
- ItemPedido
- Pagamento
- Avaliacao
- Promocao
- Evento
- Notificacao
- IA Elza

## Aggregate Root

### Local

Local é a entidade central do domínio.

Responsabilidades do Local:

- representar a identidade pública do negócio ou atrativo;
- concentrar informações comerciais e turísticas;
- conectar plano, contrato, categoria, mídia, CTA e SEO;
- servir como base para marketplace, reservas, pedidos, agenda, financeiro e analytics;
- preservar a identidade do negócio ao longo da evolução da plataforma.

Nenhum módulo futuro poderá substituir o Local como núcleo do domínio.

## Aggregate Boundaries

O agregado Local controla diretamente:

- dados cadastrais;
- categoria principal;
- status de publicação;
- plano vigente;
- contrato vigente;
- ownership;
- CTA;
- visibilidade pública;
- dados de SEO;
- mídias principais.

Entidades como Reserva, Pedido, Pagamento, Comissão e Repasse pertencem a contextos próprios e apenas referenciam Local.

Elas não devem alterar diretamente a identidade do Local.

## Usuario

Usuario representa qualquer pessoa autenticada no sistema.

Papéis principais:

- Admin;
- Empresa;
- Turista.

Os papéis serão controlados por `user_roles`.

Um Usuario pode possuir mais de um papel, conforme necessidade do produto.

## Perfil Empresa

Perfil Empresa representa um Usuario com permissão para administrar um ou mais Locais.

Responsabilidades:

- administrar seus Locais;
- atualizar dados autorizados;
- acompanhar contrato;
- gerenciar serviços;
- responder avaliações;
- acompanhar reservas e pedidos quando o plano permitir;
- acessar financeiro quando habilitado.

Perfil Empresa não substitui Local.

A Empresa é o operador.

O Local é o negócio.

## Ownership

Ownership define a relação entre Usuario e Local.

Regras:

- um Usuario pode possuir vários Locais;
- um Local possui apenas um Owner principal;
- Admin possui acesso total;
- Empresa acessa apenas seus próprios Locais;
- operações privadas exigem Ownership;
- segurança será aplicada por Supabase Auth, RLS e Edge Functions;
- o frontend nunca será camada de segurança.

## Plano

Plano define capacidades disponíveis para um Local.

Planos atuais:

- Presença;
- Destaque;
- Premium.

Regras:

- plano habilita funcionalidades;
- plano não altera a arquitetura;
- plano não cria tabelas paralelas;
- Premium desbloqueia módulos avançados;
- módulos devem consultar permissões antes de liberar recursos.

## Contrato

Contrato representa a relação comercial entre a Plataforma e a Empresa.

Responsabilidades:

- controlar plano ativo;
- controlar vigência;
- controlar status;
- manter histórico;
- preservar conteúdo mesmo em suspensão ou vencimento.

Status previstos:

- ativo;
- pendente;
- vencido;
- suspenso;
- cancelado.

Contrato não é pagamento.

Pagamentos pertencem ao domínio Financeiro.

## Value Objects

Os seguintes conceitos são Value Objects do domínio:

- Endereço;
- Coordenadas Geográficas;
- Contato;
- Horário de Funcionamento;
- Slug;
- Status de Publicação;
- Status de Contrato;
- CTA;
- SEO;
- Mídia;
- Permissão de Plano.

Value Objects não possuem identidade própria e existem como parte de entidades.

## Regras de identidade

- Local possui identidade própria e permanente.
- Slug público deve ser tratado como canônico após publicação.
- Alterações de nome não devem quebrar URLs indexadas.
- Usuario possui identidade fornecida pelo Supabase Auth.
- Contrato possui identidade própria por histórico comercial.
- Reserva, Pedido e Pagamento possuem identidade própria em seus contextos.

## Invariantes do domínio

As regras abaixo nunca devem ser violadas:

- Todo Local deve ter identidade única.
- Todo Local privado deve ter Owner definido.
- Nenhum módulo altera a identidade do Local.
- Marketplace evolui a partir de Local.
- Não existe Prestador como entidade principal paralela.
- Um Local não muda de arquitetura por causa do Plano.
- Segurança não depende do frontend.
- O legado nunca será copiado como código.
- Financeiro deve preservar histórico imutável.
- Dados públicos devem respeitar status de publicação e contrato.
- RLS deve proteger dados privados.
- Edge Functions devem proteger operações sensíveis.

## Multitenancy

O Turistei deve nascer preparado para múltiplas cidades.

A cidade inicial é Urubici.

A arquitetura deve permitir futura expansão para outros municípios sem recriar o domínio.

Preparação obrigatória:

- Local deve permitir vínculo territorial;
- categorias devem poder ser filtradas por cidade ou região;
- SEO deve preservar URLs canônicas;
- permissões administrativas devem permitir escopo futuro por cidade.

## Eventos de domínio previstos

Eventos de domínio poderão ser usados futuramente para desacoplar contextos.

Eventos previstos:

- LocalCriado;
- LocalPublicado;
- LocalAtualizado;
- ContratoAtivado;
- ContratoSuspenso;
- PlanoAlterado;
- ReservaCriada;
- PedidoCriado;
- PagamentoConfirmado;
- RepasseGerado;
- AvaliacaoRecebida.

Estes eventos não precisam ser implementados agora, mas o domínio deve permitir sua criação futura.

## Relações com módulos futuros

O Local poderá ser expandido com:

- Serviços;
- Produtos;
- Agenda;
- Disponibilidade;
- Reservas;
- Pedidos;
- Pagamentos;
- Comissões;
- Repasses;
- Avaliações;
- Promoções;
- Analytics;
- IA Elza.

Esses módulos devem ser adicionados sem reescrever o Core Domain.

## Decisões finais

- Local é o Aggregate Root principal.
- Perfil Empresa é papel operacional do Usuario.
- Plano controla capacidade, não arquitetura.
- Contrato controla relação comercial, não pagamento.
- Marketplace, Reservas e Financeiro são evoluções modulares.
- O domínio deve ser estável antes de qualquer migration importante.

## Consequência

Toda modelagem de banco, RLS, Edge Function e frontend deverá respeitar este ADR.
